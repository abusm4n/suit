\section{Methodology}
\label{sec:methodology}

\paragraph{Research Questions}
\textbf{RQ1:} Which servers and delivery paths do devices use for updates, and over which protocols?
\textbf{RQ2:} How is each update channel protected (encryption, negotiated TLS settings, server certificate), and how does this combine with the integrity protection of the delivered image?
\textbf{RQ3:} Which attacks do the observed weaknesses enable, and what do those attacks require?

\subsection{Datasets and Terms}
\label{subsec:datasets}

\paragraph{Controlled experiments}
We conducted controlled experiments using ten heterogeneous smart IoT devices, selected to represent \textbf{streaming devices} (apple-tv, fire-tv, sony-tv), \textbf{smart assistants} (homepod), and \textbf{network cameras} (d-link-cam, eufy-cam, reolink-cam, tapo-c100, tapo-c200, xiaomi-cam). 
Figure~\ref{fig:controlled_sytem_model} shows the controlled experiments setup.
First, the user agent triggered each update via the vendor's mobile app or desktop application, and the device checked, downloaded, and installed it.
The traffic was recorded using \texttt{tcpdump} on a Raspberry Pi 4 configured as a bridged wireless access point~\cite{raspi-config}, and each capture was filtered to the packets to or from the device's address.
Three devices (fire-tv, sony-tv, d-link-cam) were already up to date, so for them only an update check could be observed; seven devices downloaded and installed an update.
Figure~\ref{fig:devices} shows the controlled experiment devices.

\paragraph{Retrospective experiments}
The dataset used was generated from the Mon(IoT)r Testbed~\cite{10.1145/3355369.3355577}.
The testbed comprises 81 different IoT devices (26 unique models) deployed in the US and the UK, from which 34,586 manually controlled and automated experiments were conducted \textcolor{blue}{in 2019.
Our copy of the dataset contains 38,355 captures (37,744 interaction and 611 idle captures).
The experiments were not designed to trigger updates, so update traffic appears only where devices happened to check for or download updates.}

\paragraph{\textcolor{blue}{Terms}}
\textcolor{blue}{A \emph{capture} is one pcap file (one Mon(IoT)r experiment, or one of our update sessions).
A \emph{flow} is a bidirectional TCP connection or UDP conversation, and a TLS \emph{connection} is a flow with a TLS handshake.
An \emph{update server} is a server hostname that serves update checks, metadata, authorization, or images.
We report all counts in these units.}

\subsection{Analysis Pipeline}
For every capture we extract, with \texttt{tshark} running in parallel worker processes, DNS queries and answers, the TLS handshake messages (ClientHello, ServerHello, and certificates), HTTP request lines, Host headers, and content types, together with the timing and byte counts of each flow.
We then decide which flows belong to the update (\S\ref{subsec:attribution}); only those flows enter the channel, TLS, and certificate analyses.
Figure~\ref{fig:pipeline} gives an overview of the analysis.

\subsection{Identifying Update Traffic}
\label{subsec:attribution}
%\textcolor{blue}{\emph{Why not keywords?}
%}
A simple filter marks a capture as update-related if \texttt{software}, \texttt{firmware}, \texttt{update}, or \texttt{download} occurs anywhere in its dissected packets.
Applied to the retrospective dataset, it selects \KWsel{} captures, and Figure~\ref{fig:keyword}(a) shows where the words occur.
\KWvocab{} of the selected captures match only protocol vocabulary, most often Wireshark's TCP window-update annotation (\KWtcp{} of captures), STUN's \texttt{SOFTWARE} attribute (\KWstun{}), and SIP's \texttt{UPDATE} method (\KWsip{}).
Only 308 of them (\KWprec{}) contain traffic to a confirmed update server (below; Figure~\ref{fig:keyword}(b)).
The filter does select all 308, but \KWacc{} of them only through such unrelated fields: the names of their update servers, such as Apple's \texttt{mesu} and \texttt{gdmf} servers or Honeywell's \texttt{fwuprod}, contain none of the keywords, so the filter finds them by accident rather than by design.

\textcolor{blue}{\emph{Our approach} identifies update traffic by the servers a device talks to, in three steps.
\emph{Candidates.} We collect every hostname in DNS queries, TLS server names (SNI), and HTTP Host headers (904 distinct names in the retrospective dataset) and every HTTP request URI, and flag those that match update patterns (e.g., \texttt{update}, \texttt{upgrade}, \texttt{firmware}, \texttt{fw}, \texttt{ota}, \texttt{download}).
In our own captures we also flag the flows that carry the bulk of the bytes while the device updates.
\emph{Confirmation.} We keep a candidate only if its content or the vendor's documentation shows that it serves update checks, metadata, authorization, or images; multi-purpose device APIs that plausibly carry update commands are kept but marked \emph{likely}.
A matching name alone is not enough: \texttt{fw.ring.com} serves the doorbell's event API, and other matches are promotional downloads, alarm video clips, or advertising calls.
\emph{Assignment.} A flow is update traffic if its TLS server name or HTTP Host header, or for TLS without a server name the DNS name resolved for its server address, is a confirmed update server.
A flow on the local network counts only if its content is the image, which we verify (\S\ref{subsec:channel}).
}

\subsection{Channel Protection}

Following Ren et al.~\cite{10.1145/3355369.3355577}, we classify each update flow by protocol first: flows with a TLS or QUIC handshake are encrypted and HTTP flows are unencrypted; for both we record whether the image itself can be recovered from the traffic.
Only the remaining flows are candidates for entropy analysis.
For them we compute the normalized Shannon entropy of the flow payload, apply Ren et al.'s ranges ($H<0.4$ likely unencrypted, $H>0.8$ encrypted \emph{or compressed}, undetermined otherwise), and inspect the payload for file signatures, because high entropy indicates data that cannot be compressed further rather than encryption.

\subsection
{TLS Settings and Certificates}
\label{subsec:cipher_method}

For each update connection, we take the negotiated version and cipher suite from the ServerHello, and the offered suites from the ClientHello.
We summarize offers per distinct client configuration, because offered lists mostly reflect library defaults.
Suites are mapped to IANA names~\cite{IANA_parameters} and labelled with the four categories of the community benchmark ciphersuite.info~\cite{ciphersuite.info}, using a snapshot of its API (351 suites, included in the artifact).
Table~\ref{tab:cipher_classes} gives the criteria behind each category, examples from our data, and what each category leaves open to an adversary.
Signaling values, i.e., the renegotiation value \texttt{0x00FF}~\cite{rfc5746} and the fallback value~\cite{rfc7507}, and GREASE values~\cite{rfc8701} are not cipher suites and are excluded.

We analyze the server's \emph{leaf} certificate, i.e., the first certificate in the server's Certificate message.
Intermediate and root certificates of certificate authorities (CAs) are expected to be long-lived and are not attributes of the update server; client certificates, which a device presents in mutual TLS, are reported separately.
For each leaf, we record the issuer (a public CA or the vendor's own CA), the key type and size, and the validity period.
Key sizes map to NIST SP~800-57 security strength~\cite{NIST2020-SP800-57}: RSA-1024 provides at most 80~bits, RSA-2048 provides 112~bits, which are acceptable for applying protection only through 2030, and RSA-3072 or EC P-256 provide at least 128~bits.
We compare validity periods with the CA/Browser Forum limits for publicly trusted certificates~\cite{cabf-br}: 825~days in 2019 and 398~days since September 2020.

\subsection{\texorpdfstring{\textcolor{blue}{Image Protection}}{Image Protection}}
\textcolor{blue}{We analyze the images recovered from the traffic and, where the image was not transferred or was transferred encrypted, the vendor-published image of the installed firmware line.
We parse the file format and classify its integrity mechanism as \emph{checksum only} (such as CRC32 or MD5, which anyone can recompute), \emph{signed} (a signature that requires the vendor's private key), or \emph{signed and authorized per device} (installation also requires a per-device approval from a vendor service).
Where the format allows, we recompute the checksum to confirm it.
We do not test whether devices enforce these checks.}

\subsection{\texorpdfstring{\textcolor{blue}{Attack Preconditions}}{Attack Preconditions}}
\textcolor{blue}{Rather than querying vulnerability databases by keyword, we map each observed weakness to the weakness class (CWE~\cite{mitre-cwe}) and, where one exists, a representative CVE~\cite{CVE_Program} of the attack it enables, state what that attack requires, and record whether our data show those requirements to be met.}
